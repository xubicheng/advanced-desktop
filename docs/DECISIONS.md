## D1 · 主控 = BeagleBone Black（β 路线）　【已拍板】

| 项 | 内容 |
|---|---|
| **结论** | 采用 BeagleBone Black Rev C（TI AM3358，单核 Cortex-A8 @1GHz，512MB DDR3，4GB eMMC，micro HDMI，OSHW 认证，L1 板级开源） |
| **依据** | 用户把「全开源硬件」当硬门槛；BBB 是唯一同时满足「L1 + 86.36×53.34mm 可进鼠标壳 + 有 HDMI」的板 |
| **连带代价** | 只有 720p 实用分辨率；单核 512MB 跑不动本地 STT/LLM；只有 1 路 USB Host，必须加自供电 Hub；无板载 WiFi，需 USB 网卡 |
| **可回退性** | 中。若 BBB 断供，可换 BBB Wireless / BeagleBone Green（同尺寸同 L1），不破坏结构 |
| **否决项** | α BeaglePlay（尺寸 89×70 破 D2 形态）、γ Milk-V Mars（无 Gerber，不达 L1） |

## D2 · 形态 = 真鼠标（不做掌托式）　【已拍板】

| 项 | 内容 |
|---|---|
| **结论** | 外形 132×76×40mm 级右手人体工学鼠标，可正常抓握 |
| **依据** | 用户要求"外形必须像鼠标" |
| **连带代价** | 内部净空仅约 120×70×35mm，散热余量小；BBB 的 RJ45（高 13.5mm）与 USB-A（13mm）会在后部形成凸起；喇叭后腔只能做到 2cc 下限 |
| **可回退性** | 低。尺寸一旦定死，后续板卡只能选 ≤86×54 的 |

## D3 · 光学 = 内嵌成品 USB 鼠标模块　【已拍板】

| 项 | 内容 |
|---|---|
| **结论** | 不做 PMW3389 自研光学腔；直接内置一块成品 USB 光学鼠标裸板（含传感器+透镜+LED+光路） |
| **依据** | 用户拍板；光学腔公差是 v2 认定的最大风险项，取消后风险归零 |
| **连带代价** | BOM 不"优雅"（等于内嵌一只鼠标）；占用 1 个 USB 口（需 Hub）；无法自定义 CPI/上报率；产品叙事上"自制硬件"成色下降 |
| **可回退性** | 高。v4 若要自研，只需替换模块，接口不变（都是 USB HID） |
| **残留问题** | 成品模块的光学窗口离地高度需跟着模块原设计走（通常 1.8–2.5mm），外壳底壳开孔位置要按实际模块量 |

## D4 · 开发顺序 = Android 先行 → 投屏链路 → BBB 硬件端　【已拍板，v4 修正了理解】

| 项 | 内容 |
|---|---|
| **结论** | 先用 Android 跑通整条语音链（零硬件成本），再做「投屏到 PC + 反向指针」，最后接 BBB |
| **依据** | 用户要求；Android 手机是现成的算力与屏幕，能最快验证产品逻辑 |
| **连带代价** | Android 载体与 BBB 载体各有一套渲染器与指针注入后端（约占工时 40%）；投屏链路额外 60–140ms 延迟【需实测】 |
| **可回退性** | 高。核心层不变，砍掉任一端不影响其他端 |
| **v4 修正** | v3 曾把 D4 理解为「做三套软件（Android 版 + Windows 桌面版 + Linux 桌面版）」，**这是错的**。正确理解见 C1 |

## D5 · 许可 = 严格宽松（仅 MIT/Apache/BSD）　【已拍板】

| 项 | 内容 |
|---|---|
| **结论** | 不把 GPL/AGPL 库链接进核心；GPL 工具只允许以独立进程/CLI 方式调用 |
| **依据** | 用户要求"开源免费且商用免费" |
| **连带代价** | 禁用 piper（espeak-ng GPL-3.0）、禁用 Slint（GPL-3.0/商业）、禁用 FFmpeg 链接、禁用 Google TTS/SpeechRecognizer（闭源）；部分中文 TTS 模型需逐个核实许可；H.264 升级路径需评估 MPEG-LA |
| **可回退性** | 低。一旦链接 GPL，整个产品分发义务改变 |

## C1 · 平台范围澄清（v4 重写）　【已与用户澄清】

### 用户原话

> "Android 的操作系统要选兼容于 Windows10 以上的（Windows10, Windows11），并且也要兼容 Linux 的（包括 Ubuntu 系列，CentOS 系统等等），可以先不兼容 MacOS 和 iOS"

### v3 的错误理解（已作废）

v3 把它读成「AD 要做 Android 版 + Windows 桌面版 + Linux 桌面版**三套软件**」，并据此选了 egui 做桌面壳。**这是错的，已推翻。**

### v4 的正确理解（以此为准）

> **AD 是那台无屏计算机，显示器是别人的。** AD 的画面要能出现在 Windows 10/11 的显示器上、也要能出现在 Linux 桌面（Ubuntu 系 / RHEL 系）的显示器上。手机（Android）只是 AD 的一种**载体**，它自己的屏幕可以息屏。

| 项 | 解释 |
|---|---|
| AD 是什么 | **计算 + 语音 + 指针**的本体。**屏幕是可选外设** |
| 屏幕的两条来源 | **路 A**：BBB 原生 HDMI 直出；**路 B**：Android 把 AD 自己的画面投到 PC 显示器 |
| Windows / Linux 端的定位 | **不是 AD 的另一个版本**，而是「一台显示器 + 一只被遥控的鼠标」= **Receiver** |
| Receiver 做什么 | 只做两件事：显示 JPEG 帧、把 `PointerEvent` 注入系统光标。**不含任何 AD 逻辑** |
| UI 是否两套 | **不是**。共享「UI 状态模型 + 版式 token + 文案」；渲染器有两个（Android Canvas / BBB egui）。**像素不共享，也不假装共享** |
| 兼容基线 | Windows **10 1809（17763）+** 与 Windows 11；Linux **glibc ≥ 2.28**（Ubuntu 20.04/22.04/24.04、Rocky 8/9、Alma 8/9）。**明确不支持 CentOS 7（glibc 2.17，2024-06 EOL）与 CentOS 8（2021-12 EOL）**，不得宣传支持 |
| 不做 | macOS、iOS |
| 架构 | 一份 Rust 核心（`software/core`）+ 两个薄壳（`software/android`、`software/bbb`）+ 一个 Receiver（`software/receiver`） |
| 投屏首选 | **自渲染 + 自有 Receiver（MJPEG over TCP）**；scrcpy 作兜底；WebRTC/H.264 作将来升级 |
| 反向指针 | OTG HID → `PointerEvent` → TCP 上行 → Win `SendInput` / Linux `/dev/uinput` |

> 这条澄清已落到 [v4 方案](../v4/AD-鼠标形无屏微型计算机-设计方案-v4.md)，并推翻了 v3 的 §5.1/§5.3/§5.4。
