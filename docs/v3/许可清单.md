**落地要求：**
1. `THIRD-PARTY.md` 里每个权重必须记录：`名称 / 来源 URL / 抓取日期 / 许可文件快照 / 是否可商用`；
2. 商用版本只允许打包「已核实为 MIT / Apache-2.0 / BSD / CC-BY（非 NC）」的权重；
3. **P0（DIY 自用）阶段不涉及商用，可先用未核实权重验证链路，但必须在文档里写明「自用验证，不得对外分发」**。

### 2.3 「看着宽松、实际带毒」的核心案例：piper

**事实链：**
- `rhasspy/piper` 的代码仓库 LICENSE = **MIT**（已抓取确认）；
- 但 piper 的文本前端依赖 **`piper-phonemize`**，后者链接 **espeak-ng**；
- `espeak-ng` 的 `COPYING` = **GPL-3.0**（已抓取确认）；
- GPL-3.0 的传染性在于「链接成同一程序」→ **把 piper + espeak-ng 链进 AD 核心，AD 核心整体就必须以 GPL-3.0 发布**；
- 更直接的证据：piper 项目已迁移到新仓库 **`OHF-Voice/piper1-gpl`**，**仓库名里的 `gpl` 就是作者对许可证现状的明示**。

**结论：piper 全线禁用。** 替代：**sherpa-onnx TTS（Apache-2.0）** 或云端 TTS。

**唯一合法的用法（本项目不用，但写清楚边界）：**
- 把 piper 编译成**独立可执行文件**，AD 核心通过 `std::process::Command` 调它，用 stdin/stdout 传文本与 WAV；
- 此时 AD 核心与 piper 是两个程序，通过文件/管道通信，**不构成衍生作品**；
- 但分发时必须一并提供 piper 的源码与 GPL-3.0 文本，且用户必须能替换该二进制（GPL-3 的 anti-tivoization 条款）；
- **代价**：多一个进程、多 30–60 MB 内存、BBB 上根本跑不动 → 工程上不划算，所以不用。

| **FFmpeg** | 默认 **LGPL-2.1+**；`--enable-gpl` 则 **GPL-2.0+** | **不链接** | 仅作独立 CLI 调用（如批量转码），且**必须是 LGPL 构建**，不能用带 `--enable-gpl` 的发行版二进制 | **中-高** |

**FFmpeg 的坑（必须写清）：**
- 「FFmpeg 是 LGPL」这句话只在**默认构建**下成立；
- 一旦启用 `--enable-gpl`（为了 x264 等），整体变 **GPL-2.0+**；
- 很多 Linux 发行版自带的是 GPL 构建；
- **本项目不链接 FFmpeg**，音频编解码只用 libopus（BSD-3）与平台自带解码器（Android `MediaCodec` / Linux `libmpg123` 视需要）。

## 9. 每个依赖落地时的动作清单

1. 锁定精确版本（`Cargo.lock` / Gradle 版本目录 / 模型 commit hash）；
2. 抓取该版本的 `LICENSE` 原文存到 `docs/licenses/<组件名>.txt`；
3. 在 `THIRD-PARTY.md` 追加一行：组件 / 版本 / 许可 / 用途 / 是否修改过；
4. 若为 LGPL 动态链接：确保用户可替换 `.so`，并在文档给出替换方法；
5. 若为模型权重：记录发布页 URL 与许可字段截图，标注「可商用 / 不可商用 / 未核实」。
