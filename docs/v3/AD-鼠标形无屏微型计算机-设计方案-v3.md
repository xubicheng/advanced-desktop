## 0. 一句话结论

**用一块 86.36×53.34mm 的 BeagleBone Black 塞进 132×76×40mm 的真鼠标外壳，720p 输出，云端 STT/TTS + 本地规则降级，Android 壳先行两周跑通，硬件端最后接。这条路能走通，但代价是：鼠标重 250–300g、本地 AI 全废、USB 必须靠自供电 Hub 且要手动断路防反灌。**

## 3. D1–D3 的六项工程连带代价（逐条算）

### 3.1 外壳尺寸下限与握持方式

**约束来源（逐个量）：**

| 约束 | 数值 | 说明 |
|---|---|---|
| PCB 外形 | 86.36 × 53.34 mm | BBB 官方机械尺寸 |
| 板上最高元件 | RJ45 **13.5 mm** | 高于 PCB 顶面 |
| 次高 | USB-A 双层座 **13.0 mm** | 高于 PCB 顶面 |
| DC 座 | 11.0 mm | 高于 PCB 顶面 |
| 元件下方 | 焊点 + 支撑柱 ≥ 3.0 mm | PCB 底面到内壳底 |
| PCB 板厚 | 1.6 mm | |
| 顶壳壁厚 | 2.5–3.0 mm（ABS，FDM 打印需 ≥2.4） | |
| 底壳 + 铝板 | 2.0 + 1.5 mm | 铝板兼配重 |
| Hub 小板 + 走线 | 需 6–8 mm 净空（叠在 PCB 上方空闲区） | 不能压在 RJ45 上 |

**高度推导：** 3.0（下净空）+ 1.6（板）+ 14.0（RJ45 上方净空）+ 2.5（顶壳）+ 2.0（底壳）+ 1.5（铝板）= **24.6 mm 为绝对下限**。
但真鼠标的掌部隆起通常 38–42 mm，且需要容纳 Hub 小板与气流通道 → **取 40 mm**。高度不是瓶颈。

**长宽推导：**
- 长度方向：86.36 板 + 前部按键区 ≥18 mm（左右键 + 滚轮需 2 个 6×6 轻触或 1 个微动）+ 后部走线/接口区 ≥12 mm + 两侧壁 2×2.5 mm ≈ **121.4 mm**，取整并留 3D 打印公差 → **132 mm**。
- 宽度方向：53.34 板 + 两侧热风道各 ≥4 mm（否则侧面进风孔没有腔体缓冲）+ 两侧壁 2×2.5 mm + 侧键凸起 2×2 mm ≈ **70.8 mm**，取 76 mm 是为了给「食指/无名指夹持」留出收腰。
- **结论：外形 132 × 76 × 40 mm**（长 × 宽 × 高），体积约 401 cm³，比罗技 G502（132×75×40）几乎同尺寸。

**握持方式：掌心抓握（palm grip）**，不是指握。
- 理由：机体重量决定必须整掌承托，指握会因 250–300g 迅速疲劳。
- 前部按键区高度 22–24 mm（低于掌部 40 mm），形成 15° 左右的前倾，让食指/中指自然落在按键上。
- 宽度 76 mm 只适合掌宽 ≥ 85 mm 的手（成年男性约 P50–P70）。**掌宽 < 80 mm 的用户会觉得抓不住**——这是 D1+D2 的直接后果，不做回避。
- 尾部接口集中：DC 座、micro-HDMI、RJ45、micro-USB、microSD **全部朝后**，离握持区最远。

**重量估算（诚实）：**

| 件 | 估重 |
|---|---|
| BBB 板 | 45–55 g（含 RJ45/RJ45 屏蔽壳） |
| 4 口 Hub 小板 | 10–15 g |
| 成品 USB 鼠标模块 + 透镜支架 | 8–12 g |
| USB 声卡 + 功放 + 喇叭 | 15–25 g |
| 外壳 ABS（3.0 mm 壁厚，FDM） | 110–140 g |
| 底铝板 1.5 mm | 40–45 g |
| 线材/螺丝/散热片 | 25–35 g |
| **合计** | **253–327 g** |

对比：罗技 G502 约 121 g，MX Master 3S 约 141 g。**AD 是常规重鼠的 2–2.3 倍**。
缓解（不改决策）：① 底铝板做 1.5 mm 并在掌心正下方加厚 2 mm，把重心拉回掌心；② 壁厚从 3.0 降到 2.4（强度靠内部加强筋）；③ 后续可选「镂空减重版」外壳，减重 30–40 g 但开孔率上升影响散热与进灰。

### 3.2 USB 拓扑：成品鼠标模块 + USB 声卡 + USB WiFi 三件共存

**硬事实：BBB 只有 1 路 USB Host（USB1，Type-A），另 1 路 USB0 是 mini-USB，作 client/OTG 且与供电共用。**
→ 三件设备必须挂 Hub，没有第二条路。

**设备清单与电流：**

| 设备 | 典型 | 峰值 | 备注 |
|---|---|---|---|
| 成品 USB 鼠标模块（USB HID） | 25 mA | 100 mA | 光学传感器 + MCU，USB 2.0 Low/Full Speed |
| USB 声卡（CM108/SSS1629 类） | 30 mA | 80 mA | 48 kHz 单声道输入 + 立体声输出足够 |
| USB WiFi（RTL8188EU / RTL8192EU） | 180 mA | 450 mA | 2.4G 单频即可；5G 模块更贵更耗电 |
| **下游合计** | **235 mA** | **630 mA** | |

**Hub 选型（淘宝可得，需实测兼容性）：**

| 候选 | 芯片 | 口数 | 自供电 | 备注 |
|---|---|---|---|---|
| **首选** | FE1.1s 模块（4 口，带 5V 外供焊盘） | 4 | 是 | 便宜、货源多；需确认板上有外供 5V 输入焊盘或可割线 |
| 备选 | GL850G 模块 | 4 | 是 | 兼容性略好，部分板子无外供焊盘 |
| 备选 | SL2.1A（1 分 4） | 4 | 需改 | 多数是「一路输入四路输出」的直通板，做自供电改造麻烦 |
| 不选 | 带 DC 座的成品 Hub | — | 是 | 体积太大，塞不进鼠标壳 |

**供电与反灌防护（这是最容易翻车的一点）：**

BBB 的 USB-A 口自身会向下游输出 VBUS。如果 Hub 用系统 5V 自供电、同时上游 VBUS 还连着，那么：
- 上电时序不一致时，Hub 的 5V 会经上游 VBUS **倒灌进 BBB 的 USB 电源路径**；
- 反向电流会走 BBB 上的 USB 限流/保护器件，轻则发热，重则烧保护管；
- 更隐蔽的问题：BBB 关机而电源仍插着时，Hub 会「点亮」BBB 的 USB 子系统，出现半上电状态。

**处理方案（二选一，推荐 A）：**
- **A. 切断上游 VBUS**：剪断 Hub 上游线里的红色 VBUS 与 ID 线，只保留 D+ / D− / GND 三根，断口做热缩绝缘。Hub 全部电力来自系统 5V。
  - 合法性：USB 2.0 规范里自供电 Hub 的上游 VBUS 可以不取电，但**严格说主机侧 VBUS 不应断开**。工程实践上大量 DIY 设备这么做且工作正常，但它不属于「完全合规」。**如实标注：这是工程妥协，不是规范做法。**
- **B. 串理想二极管 / ORing**：在上游 VBUS 串一只 SS34 肖特基（正向压降 0.3–0.5V）或理想二极管芯片（如 LM66100）。规范上更干净，但多 0.3V 压降、多一个元件、多一处焊点。

**会不会拖垮 5V 预算？→ 会，所以电源必须升级到 5V/4A。** 详见 §3.5 的电流预算表。

**物理布置：**
- Hub 小板放在 PCB 上方、RJ45 之后的空闲区（约 30×20 mm 可用），双面胶 + 尼龙柱固定。
- 上游线用 20 cm 的 USB-A 公对母短线改线；下游三根线用 15 cm 短线，全部从 Hub 同一侧出线并扎带固定。
- WiFi 天线：USB 模块自带 PCB 天线会被金属底板和 BBB 的 RJ45 屏蔽壳遮挡 → **必须选带外置天线（IPEX 转 SMA 或 PCB 天线延长到外壳尾部）的型号**，天线贴在外壳尾部内壁。这是 D1 的直接代价：BBB 无板载 WiFi。

### 3.3 720p 输出对 UI 与 AI 界面的影响

**为什么是 720p 而不是 1080p：**
1. AM3358 的显示子系统（LCD 控制器 → TDA19988 HDMI 编码器）在 1080p60 下带宽与时序余量已经很紧，单核 A8 上跑合成器开销显著；
2. 512 MB 内存下，1080p 双缓冲 + UI 纹理占用翻倍；
3. 720p 下 UI 元素放大后，**在 24 寸显示器上的实际视认尺寸与 1080p 小字号相当**，反而更清晰。

**关键换算（供设计参考）：** 24 寸 16:9 显示器宽 531 mm / 1280 px → 像素间距 0.415 mm。在 600 mm 观看距离下，1 px ≈ 2.4 角分。人眼舒适阅读的下限约 12–15 角分/字高（x-height），因此**正文 ≥ 24 px 是硬性下限，26 px 更稳**。

**720p UI 规范（写死，Android 壳与桌面壳共用同一套 token）：**

| 项目 | 规定值 | 理由 |
|---|---|---|
| 画布 | 1280 × 720 | |
| 安全边距 | 上下左右 5%（64 / 36 px） | 电视过扫描 + 显示器边框 |
| 正文 | 24 px，行高 1.5（36 px） | 硬下限 |
| 标题 | 40 px | |
| 次级文字 / 时间戳 | ≥ 20 px，且必须加深色底 | 20 px 是绝对下限，不可再小 |
| 按钮高度 | ≥ 64 px，最小点击区 64×64 | |
| 图标 | ≥ 32 px，线宽 ≥ 2 px | 1 px 细线在 720p 上会和扫描线打架 |
| 对比度 | ≥ 7:1（AAA） | 暗背景 + 亮字 |
| 配色 | 深色底 `#12141A`，主文字 `#F2F4F8`，强调 `#5AC8FA` | 减少屏幕亮度对暗环境的干扰 |
| 每屏卡片数 | ≤ 3 | 超过 3 项必须分页/滚动 |
| 分栏 | **禁止左右双栏** | 720p 双栏会让每栏 < 500 px，正文宽度不足 |
| 动画 | ≤ 200 ms 的淡入淡出，禁位移 | 单核 + 软件栅格化，位移动画会掉帧 |

**AI 界面的具体形态（720p 下唯一可行的布局）：**
- **语音优先**：屏幕不是主交互面，TTS 是主输出。屏幕只承担「我在听 / 我在想 / 我在说 / 出错了」四态可视化。
- 布局：**单列三区**——顶部 40 px 状态条；中部「最近一轮对话」（用户那句 + 助手那句，各限 3 行，超出语音播报不显示）；底部 96 px 操作条（一个 96×96 的「按住说话」大按钮 + 一个「取消」）。
- 历史对话不做全量列表，只做「上一条 / 下一条」翻页（每页 1 轮），因为 720p 一屏放不下 3 轮以上还保持 24 px。
- 长文本回答：**只播报 + 只显示前 200 字**，其余「详见手机/电脑端」——这条很重要，720p 上读长文是折磨。

### 3.4 单核 1GHz + 512MB 跑本地语音的现实结论

**结论先给：本地 STT 和本地 TTS 都不可用。默认云端，本地只保留 6–10 条预录提示音。**

**算力基线：** AM3358 = Cortex-A8 单核 @1 GHz + NEON（128-bit SIMD，但无 AArch64，无 dot-product 指令）。A8 的 NEON 是 64-bit 寄存器对拼成的 128-bit，实际 SIMD 吞吐约为同频 Cortex-A53 的 **1/2 – 1/3**，且无异步流水。

**实测预期（基于同类 A8/A7 单核公开数据外推，本地未实测，标注「需实测」）：**

| 任务 | 模型 | 预期速度 | 3 秒音频耗时 | 可用性 |
|---|---|---|---|---|
| STT | whisper.cpp tiny（39M） | 实时 1/5 – 1/10 | 15–30 s | **不可用** |
| STT | whisper.cpp tiny.en q5_1 | 实时 1/4 – 1/8 | 12–24 s | **不可用** |
| STT | sherpa-onnx zipformer-small | 实时 1/3 – 1/5 | 9–15 s | **不可用** |
| STT | Vosk small-cn（Kaldi） | 实时 1/2 – 1/4 | 6–12 s（流式，首字更久） | **不可用** |
| TTS | VITS 中文（~30M） | 实时 1/5 – 1/10 | 一句 5 s 语音需 25–50 s | **不可用** |
| TTS | sherpa-onnx 轻量 VITS | 实时 1/3 – 1/5 | 一句 5 s 需 15–25 s | **不可用** |
| 唤醒词 | openWakeWord / Porcupine | 常驻 3–8% CPU | — | 勉强可用，但**不做**（见下） |
| 预录 WAV 播放 | — | 0 | 0 | **采用** |

**内存：** 512 MB 总量，系统 + 驱动 + 桌面壳常驻约 180–260 MB，剩余 250–330 MB。whisper tiny 的 ggml q5_1 约 42 MB、运行时峰值再 +100 MB；VITS 约 60–120 MB。**单看内存勉强够，但 CPU 时间完全不够，内存不是瓶颈，算力才是。**

**所以运行时策略：**

```
按键按下
  → 录音（16 kHz / 16-bit / 单声道，≤ 30 s 环形缓冲）
  → 网络探测（≤ 300 ms）
      ├─ 通：上传 → 云端 STT → LLM → 云端 TTS → 边下边播
      └─ 断：① 播报预录「网络不可用」 ② 进规则引擎（本地关键词匹配）
```

**本地保留的东西（很小，但值得）：**
- 6–10 条预录提示音（16 kHz WAV）：`我在听` / `没听清` / `网络不通` / `已取消` / `正在想` / `好了` / `出错了` / `电量低`。单条 ≤ 1.5 s，合计 < 200 KB。
- 一个规则引擎（纯 Rust，无模型）：识别「音量加/减」「静音」「暂停」「继续」「打开设置」「关机」等 10–15 条固定指令，用云端 STT 的文本做匹配；完全断网时退化为「只能按键」，不假装能听懂。
- **不做唤醒词常驻监听**：单核常驻 3–8% CPU 换一个「不用按键」的便利，不值得；且唤醒词模型（openWakeWord 是 Apache-2.0，Porcupine 闭源）在 A8 上的误唤醒率与延迟都需实测，风险大于收益。

**延迟预期（端到端首音，标注「需实测」）：**

| 段 | 预期 | 变量 |
|---|---|---|
| 按键松手 → 录音封包 | 20–50 ms | 本地 |
| 上传（2.4G WiFi，3 s/48 KB opus） | 80–400 ms | 信号强度 |
| 云端 STT 首字 | 200–600 ms | 服务商 |
| LLM 首 token | 300–1500 ms | 模型与负载 |
| 云端 TTS 首包 | 200–600 ms | 流式与否 |
| 下行 + 解码 + 播放起始 | 60–150 ms | BBB 上 mp3/opus 解码开销 |
| **合计（首音）** | **0.9 – 3.3 s** | |
| 稳定态（后续句子） | 每句 +0.6–1.5 s | 流式可压到 0.4 s |

**降级三级：**
1. 云端全通 → 正常；
2. 网络通但云服务超时（> 5 s 无首包）→ 播报「服务慢，先记下」，把语音存本地队列，恢复后补处理；
3. 完全断网 → 预录提示音 + 规则引擎 + 屏幕显示「离线模式」，**不尝试本地识别**（省得用户等 20 秒换来一句「没听懂」）。

### 3.5 micro-HDMI 与供电

**视频接口：**
- BBB 是 **micro-HDMI（Type D）**，经 TDA19988 编码器，最高 1920×1080。
- 必须配转接。**推荐：micro-HDMI 公 → HDMI 母 的 20 cm 软排线转接头**（不是硬转接头）。
  - 硬转接头 + HDMI 线自重会形成杠杆，micro-HDMI 座是贴片焊、**最容易被拽掉**，这是 BBB 上的高发故障。
  - 软排线转接可从尾部出线，外壳上做应力消除（线卡 + 硅胶）。
- 外壳尾部开一个 12×8 mm 的过线孔，孔内加 TPU 护线圈。
- 需要 HDMI 线材本身另购（1.5–2 m，HDMI 2.0 认证线即可，720p 对线材不挑）。

**供电（这是 BBB 的第二个坑）：**

| 方式 | 能力 | 结论 |
|---|---|---|
| DC 5.5×2.1 barrel（中心正） | 官方设计路径，5V，理论 4A 级 | **采用** |
| micro-USB（USB0） | 板上有限流与保护，实践 **≤1 A**，线与口都受不了 | **不用**（仅作串口调试） |
| USB-C 转接板 | BBB 无 USB-C，需外挂 PD 诱骗 + 5V 直供 | 多一层故障点，不采用 |

**电流预算（峰值，标注「需实测校准」）：**

| 负载 | 典型 | 峰值 |
|---|---|---|
| BBB 本体（SoC + DDR + eMMC + HDMI + PHY） | 0.55 A | 1.10 A |
| Hub 芯片自身 | 0.02 A | 0.05 A |
| 下游三件（鼠标 + 声卡 + WiFi） | 0.24 A | 0.63 A |
| 功放 PAM8403（2×3W，播报语音时） | 0.15 A | 0.90 A |
| 风扇（后备方案，常关） | 0 | 0.08 A |
| **合计** | **0.96 A** | **2.76 A** |

- 电源选 **5V / 4A（20 W）**，留 45% 余量。5V/3A（15 W）在「WiFi 峰值 + 喇叭大声 + SoC 满载」三件事同时发生时余量只有 8%，会出现欠压重启。
- 线材：**≥ 20 AWG，长度 ≤ 1 m**。24 AWG 的 1.5 m 线在 2.8 A 下压降约 0.35–0.45 V，直接掉到 4.55 V，触发欠压。
- 验收线：**满载时 DC 座入口电压 ≥ 4.90 V，BBB 板上 5V 测试点 ≥ 4.75 V**。低于此值一律判定供电不合规。
- 入口保护：自恢复保险丝（MF-R110，1.1 A 保持 / 2.2 A 跳脱）—— 注意 **1.1 A 保持电流 < 2.76 A 峰值**，会误跳。正确做法：**用 3 A 保持（MF-R300）**，或改用 2 A 快断玻璃管 + TVS（SMAJ5.0A）。这里明确写清楚，避免照抄 v2 的 1.1 A。
- 反面教材：不要用「5V 2A 手机充电头 + 24 AWG 细线」，这是 BBB 论坛上最常见的「随机重启」根因。

### 3.6 BBB 断供 / 买不到时的 L1 降级链

**原则：只在 L1（板级全开源：原理图源文件 + PCB + Gerber + OSHW 认证或 CERN-OHL 许可）内降级，绝不退回 H618 / 树莓派 / 电视棒等专有板。**

| 级别 | 板 | 关键差异 | 对方案的影响 | 供货判断 |
|---|---|---|---|---|
| **T0（主选）** | BeagleBone Black（AM3358） | 基准 | — | 国内需代购/现货商，**需询价**，¥400–520 |
| T1 | **BeagleBone Black Wireless** | 同 SoC，**去掉 RJ45、加板载 WiFi** | **正面**：省掉 USB WiFi（下游少 450 mA 峰值）、省掉 RJ45 的 13.5 mm 高度 → 壳高可降到 34 mm；**负面**：802.11 b/g/n 2.4G，吞吐一般 | 需询价 |
| T2 | **BeagleBone Green / Green Wireless**（Seeed） | 与 BBB 同 SoC，去 DC 座改 micro-USB 供电、加 Grove 接口 | **负面**：micro-USB 供电上限 1 A 不够 → 需自己焊 5V 输入或加 USB-C 供电小板；Green Wireless 同样带 WiFi | 需询价；板级文件需确认是否完整 |
| T3 | **BeaglePlay**（AM6254） | 4×A53 / 2 GB / 全尺寸 HDMI / 板载 WiFi / 89×70 mm | **破形态**：89×70 塞进 132×76 的鼠标壳后，按键区与走线区被挤掉 → 只能改掌托式（160×95×45，回到 v2 形态）或加大到 145×88×45（已不像鼠标）。性能反而够跑本地 STT | 需询价，¥850–1100 |
| T4 | **BeagleBone AI-64**（TDA4VM） | 6 核 A72 + 2 TOPS | 性能过剩、价格 ≥¥1500、板更大 | 需询价 |
| **禁止** | H618 / 树莓派 / 电视棒拆板 / Milk-V Mars | 板级不开源（Mars 仅 PDF 原理图，无 Gerber，属 L1.5） | — | — |

**决策树：**

```
BBB 现货可买？
├─ 是 → 按本文执行
└─ 否 → BBB Wireless 可买？
        ├─ 是 → 切 T1（同时删掉 USB WiFi 与 RJ45 开孔，壳高 40→34 mm，电源可降到 5V/3A）
        └─ 否 → BeagleBone Green Wireless 可买？
                ├─ 是 → 切 T2（必须解决 5V 供电改造）
                └─ 否 → 是否接受「形态从鼠标退回掌托式」？
                        ├─ 是 → 切 T3 BeaglePlay（同时获得本地 STT 能力，§3.4 结论作废）
                        └─ 否 → **暂停硬件端，只做 Android + 桌面端软件**，等货
```

**注意：T3 会让 §3.3（720p）与 §3.4（本地语音判死）两条结论同时失效** —— 这是升级路径，不是等价替换。切换时必须重写对应章节，不能直接套用。

### 4.2 关键接口定义

| 接口 | 方向 | 说明 |
|---|---|---|
| DC 5.5×2.1 | 入 | 5V/4A，中心正，**反接保护必须做**（SMAJ5.0A 只能防过压，不防反接 → 加一只 SS54 串联，或选带防反接的 DC 座） |
| micro-HDMI | 出 | 720p60，转接软排线到尾部 |
| RJ45 | 双向 | 可不用（WiFi 优先），但保留可作有线回退；开孔在尾部 |
| micro-USB | 双向 | 仅调试（串口 console + 固件烧写），正常使用时拔掉 |
| microSD | — | 系统可从 eMMC 启动，microSD 作救砖/扩容 |
| 按键 | 入 | 前部：左键 / 右键 / 滚轮中键；侧部：PTT（按住说话）+ 音量 |
| 指示灯 | 出 | 1 颗 RGB 或双色（录音中=红，联网中=蓝，就绪=绿） |

**按键方案说明：** D3 用成品 USB 鼠标模块，模块自带左右键与滚轮，**这些按键通过 USB HID 上报，不经过 BBB 的 GPIO**。
→ 所以「鼠标按键」与「PTT」是两套东西：
- 左/右/中键 = 模块原生 HID，直接当鼠标用（这是产品语义）；
- **PTT 必须另加一个独立的物理按键**，接 BBB 的 GPIO（或接一个独立的 USB HID 小键盘模块），因为「按住说话」不能被鼠标左键占用。
- 推荐：PTT 用侧面的一个大行程轻触（6×6×5 mm 或 12×12 轻触），接 GPIO，软件里做 20 ms 去抖 + 长按 200 ms 触发。

### 4.3 音频链路

```
[模拟驻极体麦克风 或 USB 声卡自带麦]
   → USB 声卡（48 kHz 采集，ADC）
   → ALSA (arecord / cpal) 16 kHz 单声道重采样
   → Rust 核心（opus 编码，20 ms 帧）
   → 云端 STT

[云端 TTS 返回 opus/mp3]
   → Rust 核心解码 → 48 kHz PCM
   → USB 声卡（DAC）
   → PAM8403 功放（3.5 mm 或焊接输入）
   → 8Ω 2W 喇叭（装在壳体前部，出声孔朝前下方）
```

**为什么不走 I2S：** BBB 的 I2S 引脚在 P9 排针上可用，但要额外接 codec（如 PCM5102 / ES9023）+ 麦克风 ADC（如 INMP441 是 I2S 数字麦），会引入 3–4 处手工焊接与时钟匹配问题。**用 USB 声卡是「零焊接、即插即用」的路线，符合 D3 的「不造轮子」精神。**
代价：多占一个 Hub 口、多 30–80 mA、多 10–15 g。

**喇叭位置：** 前部下方，出声孔朝前下 45°，避开手掌遮挡；腔内做 3 mm 深的独立音腔（用泡棉围一圈），否则会听到壳体共振。

### 4.4 光标链路

```
成品 USB 鼠标模块（光学传感器 + MCU）
   → USB HID（标准鼠标描述符）
   → Linux usbhid 驱动
   → /dev/input/eventX
   → （可选）Rust 核心读取事件做「手势/长按」判断
   → X11/Wayland 光标
```

**与 v2 的差别：** v2 是「传感器芯片 + uinput 注入 REL_X/REL_Y」，v3 是「完整 HID 设备」，内核驱动栈原生支持，**零驱动开发**。
**代价：** 模块外形固定（多为 25×20 mm 级小板 + 透镜），透镜到桌面的距离由模块决定，**外壳底部必须按模块的光学高度开孔**（通常透镜下沿距桌面 1.2–2.0 mm），这个高度要在 3D 打印时预留可调垫片，否则光标会飘或不动。

**必须实测的：** 模块的 DPI 与加速度曲线。低价模块常见 800/1200 DPI 固定档，不可调，且**在 BBB 的 512 MB 与 720p 下，高 DPI 会造成光标「飞」** → 建议选支持 1000 DPI 或可在 Linux 下用 `xinput --set-prop` 降速的模块。

### 5.1 三族平台与兼容基线（写死）

| 平台族 | 最低基线 | 明确不支持 | 备注 |

**关于 CentOS 的诚实说明：** 用户原话提到「CentOS 系统」。CentOS Linux 8 已 EOL、CentOS 7 也已于 2024-06-30 EOL，其 glibc 2.17 无法运行现代 Rust/Tauri/egui 构建产物。因此本方案的表述统一为「**RHEL 系（以 Rocky Linux 8/9、AlmaLinux 8/9 为准）**」，**不是**宣称支持 CentOS 7/8。这一点写进 README 与兼容矩阵，避免后续验收扯皮。

**为什么 Windows 基线是 1809 而不是 7/8.1：** egui/eframe 依赖 winit + wgpu/DX12，winit 的 Windows 后端最低支持 Win7 但 wgpu 的 DX12 后端需要 Win10；且 1809 是微软仍提供安全更新的较老 LTS 分支（企业 LTSC 2019 基线）。

### 5.2 核心 C ABI（一份，三端共用）

核心用 Rust 编写，编译为 `cdylib`，对外只暴露 C ABI。**Android 走 JNI 手写绑定，Windows/Linux 走 Rust 原生链接，BBB 走同一份 cdylib。**

```c
typedef struct AdCallbacks {
    void (*on_event)(const char *json, void *user);          // 状态/结果事件
    void (*on_pcm)(const int16_t *pcm, int frames,
                   int rate, void *user);                     // TTS 音频流
} AdCallbacks;

void *ad_core_new(const char *config_json, AdCallbacks cb, void *user);
int   ad_core_start_listen(void *h);       // 开始录音
int   ad_core_end_listen(void *h);         // 结束录音，触发 STT→LLM→TTS
int   ad_core_push_pcm(void *h, const int16_t *pcm, int frames, int rate); // 外部灌音频
int   ad_core_cancel(void *h);             // 打断当前回合
int   ad_core_set_mode(void *h, int mode);  // 0=auto 1=cloud-only 2=local-only
int   ad_core_get_state(void *h);           // 0=idle 1=listen 2=think 3=speak 4=error
void  ad_core_free(void *h);
```

**为什么不用 UniFFI：** UniFFI 是 MPL-2.0（文件级 copyleft），虽然生成绑定属工具用途、一般可接受，但它会引入 `uniffi` 运行时依赖、增加 .aar 体积、且 Kotlin 侧生成代码量大。**手写 JNI（`jni` crate，MIT/Apache-2.0）约 200 行，可控、零传染、体积最小。**

**事件协议（JSON，`on_event` 载荷）：**

```json
{"t":"state","v":"listen"}
{"t":"partial","text":"帮我查一下明天"}
{"t":"final","text":"帮我查一下明天的天气","latency_ms":1420}
{"t":"reply","text":"明天南京多云，12 到 21 度","src":"cloud"}
{"t":"error","code":"NET_TIMEOUT","msg":"STT 超时 5s","fallback":"local_rule"}
{"t":"fallback","v":"offline"}
```

### 5.3 桌面壳框架取舍（Tauri vs egui vs Slint）

| 维度 | **egui / eframe** | Tauri 2.x | Slint |
|---|---|---|---|
| 许可证 | MIT OR Apache-2.0 ✅ | MIT OR Apache-2.0 ✅ | **GPL-3.0 或商业授权** ❌ |
| 二进制体积（Release，单 exe） | **≈ 5–8 MB** | ≈ 8–15 MB + **依赖系统 WebView2** | ≈ 6–10 MB |
| Windows 依赖 | 无（自带 OpenGL/DX 后端） | **必须装 WebView2**（Win10 1809 需手动引导安装） | 无 |
| Linux 依赖 | libxkbcommon / libgl / libasound2 | **WebKitGTK 4.1**（Rocky 8 无包，需自行编译，破坏兼容基线） | libxkbcommon / libgl |
| 内存占用（空窗） | **≈ 40–60 MB** | ≈ 120–200 MB | ≈ 50–80 MB |
| 512 MB 内存适配 | ✅ 最好 | ⚠️ 吃力 | ✅ |
| 720p 固定布局 | ✅ 立即模式，像素级可控 | ✅ HTML/CSS 更灵活 | ✅ 声明式 |
| 中文输入 | ⚠️ 需自己接 IME（egui 对 IME 支持弱） | ✅ 原生支持 | ⚠️ 有限 |
| 学习/维护成本 | 低（纯 Rust） | 中（Rust + 前端栈） | 中（自研 DSL） |

**结论：egui 定案。** 理由排序：① Slint 的 GPL-3.0 直接违反 D5，淘汰；② Tauri 的 WebView2/WebKitGTK 依赖会同时破坏「Win10 1809 开箱即用」与「Rocky 8 兼容」两条基线，且内存翻 3 倍；③ egui 在 512 MB 与 720p 固定布局下最稳。
**已知短板与对策：** egui 的中文 IME 支持弱 → 桌面壳的文本输入框只用于「输入 API Key / 设置项」这类低频场景，主交互是语音；确需长文本输入时，提供「用系统默认程序打开配置文件」的兜底。

**Tauri 备选触发条件（写清，避免以后反复）：** 仅当出现下面任一情况才考虑换 Tauri —— ① 目标 Windows 机器显卡过老、OpenGL 只有 1.1 且无 DX12；② 产品需要复杂富文本/表单；③ 团队更熟 Web 前端。换壳时必须同步修改兼容基线文档。

## 6. 散热（真鼠标形态重算）

### 6.1 与 v2 的差别

v2 是 160×95×45 的掌托大壳，散热面积约 3.2 倍于鼠标壳。**缩到 132×76×40 后，外表面积从 ≈ 0.081 m² 降到 ≈ 0.043 m²（减少 47%），而发热量不变。** 这是本版最硬的一处物理约束。

### 6.2 材质

| 件 | 材质 | 理由 |
|---|---|---|
| 主体外壳 | **ABS**（FDM 打印，壁厚 2.4–3.0 mm） | Tg ≈ 100 °C，热变形温度 88–95 °C，比 PETG（Tg 75–80 °C）安全得多。SoC 附近内壁实测可能到 70–80 °C，PETG 会软塌 |
| 底盖 | **5052 铝板 1.5 mm**（激光切割或手工锯 + 锉） | 兼导热与配重，把重心压到掌心下方 |
| 按键 | ABS（同主体，一体打印） | |
| 喇叭音腔围边 | 3 mm EVA 泡棉 | 隔振，避免壳体共振 |
| 屏幕/接口过线护圈 | TPU（95A） | 应力消除 |

**不选 PETG 的理由要写清：** PETG 打印更容易、更耐摔，但 75–80 °C 的 Tg 在「SoC 满载 30 分钟」场景下，靠近散热片的顶壳内壁会软化、螺丝柱会蠕变。**如果只有 PETG 可用，必须把锁频降到 600 MHz 且顶壳必须开格栅**（见 6.5 后备 1）。

### 6.3 开孔策略

| 位置 | 开孔 | 数量/尺寸 | 开孔率 | 说明 |
|---|---|---|---|---|
| **顶面** | **不开** | 0 | 0% | 手掌整面贴合，开孔=手感灾难 + 大量进灰 + 直接烫手 |
| 左侧面（前 1/3） | 进风 | φ2.0 mm × 6 | 侧面积 ≈ 1.8% | 位于食指下方凹陷处，不挡握持 |
| 右侧面（前 1/3） | 进风 | φ2.0 mm × 6 | ≈ 1.8% | 对称 |
| 底部（后半段） | 出风 | φ2.0 mm × 12 | 底面积 ≈ 1.5% | 靠后，避免手掌遮住；铝底板上同位置开对应孔 |
| 前部（喇叭） | 出声 | 1.5 mm 蜂窝 × 9 | — | 与散热孔分开，避免气流声 |
| **总散热开孔率** | | **3.3–3.6%** | | 目标区间 3–4% |

**为什么是「侧进 + 底出」而不是「底进 + 顶出」：** 顶面被手掌完全覆盖，气流无法从顶部排出；侧面与底部是唯二不被遮挡的边界。热空气在腔内上升 → 沿内壁下沉 → 从底部孔排出，形成弱烟囱。这个气流很弱（无风扇），主要靠自然对流 + 壳体导热。

**开孔与手感/进灰的权衡（明确写）：**
- 开孔率每 +1%，腔内温度约降 1.5–2.5 °C（经验值，需实测），但进灰速率约 +25%。鼠标放在桌面上，底部孔会吸入桌面灰尘与绒毛，**3 个月左右需要清一次**（拆底盖，软毛刷 + 气吹）。
- 侧面孔位于握持凹陷处，手指会摸到孔边 → 必须做**倒角 0.5 mm + 内侧加防尘网（80 目尼龙网，双面胶固定）**，否则手感毛刺。
- **不做**「大面积网格」：鼠标是手持物，任何大于 φ3 mm 的孔都会让指尖陷进去。

### 6.4 导热路径

| 件 | 规格 | 位置 |
|---|---|---|
| 散热片 | 铝，**20×20×8 mm**，鳍片 8 片，导热胶预贴或自贴 | AM3358 顶面，正对腔内中央 |
| 导热垫 | **1.0 mm，导热系数 ≥ 3 W/m·K**（如莱尔德 Tflex 300 类） | 散热片底部与 SoC 之间 |
| 铜箔（可选） | 0.1 mm 自粘铜箔，宽 15 mm | 从散热片侧壁贴到左侧内壁，把热引到壳体 |
| 铝底板 | 5052，1.5 mm | 底盖；与 Hub/功放之间加 0.5 mm 导热垫（这两件也发热） |

**主散热路径的现实说明：** 没有风扇、没有热管，热量路径是「SoC → 散热片 → 腔内空气 → 内壁 → 外壳 → 空气」，热阻大约 6–10 °C/W（需实测）。这意味着 **SoC 每发 1 W，壳温相对环境升高 6–10 °C（在 3.5% 开孔率下）**。AM3358 满载约 2–2.5 W → 壳温比环境高 12–25 °C。室温 25 °C 时壳温 37–50 °C，**刚好卡在 45 °C 目标的边缘**。所以「锁频 800 MHz」不是保守，是必需。

### 6.5 锁频与软件降压

| 参数 | 值 | 做法 |
|---|---|---|
| CPU 上限频率 | **800 MHz**（默认 1 GHz） | `cpufreq-set -u 800MHz`，或改 `/etc/default/cpufrequtils` |
| governor | `ondemand` 或 `schedutil` | 不用 `performance`（会一直全速） |
| 空闲降频 | `powersave` 下限 300 MHz | 待机时几乎不发热 |
| 以太网 PHY | **不用时 down 掉**（`ip link set eth0 down`） | 省 0.15–0.25 W |
| HDMI 输出 | 无外接显示器时可关（`vc`/DRM 关闭） | 省 0.1–0.2 W；但**产品形态是有屏的**，此条只用于待机 |
| 关闭未用外设 | 禁用未用 UART/SPI/I2C 时钟 | 边际收益，可选 |

### 6.6 验收目标

| 指标 | 目标 | 测法 |
|---|---|---|
| 外壳顶面温度（手掌接触区） | **≤ 45 °C** | 满载 30 min 后，红外枪贴 5 点取最高 |
| SoC 结温 | **≤ 85 °C**（不触发降频） | `cat /sys/class/thermal/thermal_zone0/temp` |
| 是否降频 | 无（`cpufreq` 统计里 `time_in_state` 不出现 1 GHz 档） | |
| 测试负载 | `stress-ng --cpu 1 --vm 1` + 循环播放 TTS + WiFi 持续传输，30 min | |

**如果 30 分钟时顶面 > 45 °C，两级后备：**

| 级别 | 措施 | 代价 | 预期收益 |
|---|---|---|---|
| **后备 1（结构）** | 顶面靠后 1/3 开 **20×40 mm 细格栅**（1.2 mm 缝 × 8 条），开孔率 +8%（总 11–12%） | 手感变差（掌心能感到格栅）、进灰加速 2 倍、外观变「游戏鼠标风」 | 壳温降 5–8 °C |
| **后备 2（主动）** | 尾部加 **5V 20×20×6 mm 风扇**（Noctua NF-A4x10 5V 或同级），从尾部吸入、底部排出 | +80 mA（电源余量仍够）、噪音 15–20 dBA、多一个开孔与滤网、多 12 g | 壳温降 12–18 °C |
| 后备 3（降级，不推荐但可用） | 锁频降到 600 MHz + 关 WiFi 改有线 | 性能再降 25%，WiFi 功能丧失 | 壳温降 4–6 °C |

**顺序：先试后备 1（只改打印件，成本 0），不行再上后备 2（+¥25）。**
