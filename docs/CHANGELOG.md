# CHANGELOG

## v4.0 — 2026-11-06（概念模型修正：AD ≠ 桌面软件）

> **一句话：把「AD 要做三个平台版本」改成「AD 只有一个本体，屏幕是可选外设」。**
> 这是本版唯一的概念变更，但它推翻了 v3 的整个软件架构章节。

### 4.1 为什么改（用户澄清）

v3 把 D4 理解成「AD 要做 Android 版 + Windows 桌面版 + Linux 桌面版」三套软件，并据此选了 egui 做桌面壳。

用户澄清后，正确理解是：

> **AD 是那台无屏计算机，显示器是别人的。** AD 的画面要能输出到 Windows 10/11 的显示器上、也要能输出到 Linux（Ubuntu 系、CentOS 系）的显示器上。手机（Android）只是 AD 的其中一种**载体**，手机自己的屏幕可以息屏。

这个差别不是措辞问题：**它把「Windows/Linux 端」从「AD 的另一个版本」降级为「一台显示器 + 一只被遥控的鼠标」**，工程量、许可面、体积、维护成本全部改变。

### 4.2 改了什么

| # | 变更点 | v3 | v4 | 影响章节 |
|---|---|---|---|---|
| 1 | **概念模型** | 三族平台 + 一套核心多端外壳（三个完整 UI） | **AD 本体（计算+语音+指针）+ 可选屏幕**；两个渲染器 + 一个 Receiver | v4 §1，取代 v3 §5.1 |
| 2 | **桌面端定位** | 「Windows/Linux 桌面壳 = AD 的一个客户端」 | **Receiver = 外设**：只显示帧、只注入指针，不含 AD 逻辑 | v4 §2、§3 |

| 4 | **桌面技术栈** | egui / eframe（需要 OpenGL 3.3 或 DX12） | **winit + softbuffer（纯 CPU 位图 blit，零 GPU 要求）** | v4 §6.1 |

| 10 | **兼容基线收窄并写死** | Win10 1809+ / glibc ≥2.28（已写） | 沿用，并**明确 Receiver 的分发形态与不支持的发行版**（CentOS 7/8 明确不支持） | v4 §6 |
| 11 | **两周计划扩展为四周** | W1–W2 语音，W3–W4 桌面壳 | W1–W2 语音（UI 改为渲染到 Bitmap）；**W3 投屏打通；W4 反向指针 + 息屏实测** | v4 §8 |
| 12 | **能力差异表写死** | 分散在正文 | BBB 与 Android 载体逐项对照（分辨率 / 本地模型 / 直出 HDMI / 功耗 / 延迟） | v4 §7.2 |
| 13 | **新增风险 7 条** | 无 | 编码帧率、ROM 限流、uinput 权限、UAC 边界、USB 授权弹窗、UI 漂移、认知偏差 | v4 §9 |

### 4.3 技术纠偏（对用户描述的修正，必须记）

| 用户描述 | 我的判断 | 处理 |
|---|---|---|
| 「MVP 建议 MJPEG over TCP，Android 自带 `YuvImage`/JPEG 编码」 | **方向正确，API 选错**。`YuvImage` 吃 NV21/YUV420，是给相机预览用的；我们自渲染的产物本来就在 `Bitmap` 里（ARGB_8888），应该用 `Bitmap.compress(JPEG, q, out)`，一行搞定，无需 YUV 转换 | 采纳「MJPEG over TCP」，改用 `Bitmap.compress`；q 取 72–80 |
| 「方案 1 优点：可完全息屏（不依赖 MediaProjection 抓屏）」 | **判断正确且是关键优势**。自渲染与屏幕是否点亮无关 | 作为首选方案的核心理由 |
| 「方案 2 scrcpy 兜底」 | 同意做兜底，但要说清它的两个硬伤：**镜像的是整块手机屏**（含状态栏/通知），以及**每次连接要授权 USB 调试** | 列为兜底，触发条件写死 |
| 「方案 3 WebRTC/H.264」 | 同意「功能强但许可与体积是大问题」；补充：**H.264 的 MPEG-LA 专利池**在自用场景无碍，分发场景需评估 | 列为将来升级路径，给出 4 个切换点 |

## v3.0 — 2026-11-06（β 路线定稿）

> 触发原因：用户拍板 D1–D5，要求 v3 方案 + Android 优先落地计划 + 淘宝优先采购清单，并把项目建公开仓库上云。
> 本版是 **v2 的收敛版**：不再给候选，只给一条路，并把这条路的代价算到底。

### 3.1 决策落定带来的变更

| # | 变更点 | 原因 | 影响 |
|---|---|---|---|
| 1 | **主控定为 β = BeagleBone Black（AM3358 单核 1GHz / 512MB / 4GB eMMC）**，BeaglePlay 从「首选」降为「降级链 T3」 | 用户 D1 拍板 β | 性能天花板从 4 核/2GB 降到单核/512MB；本地 AI 全部作废（见 #7） |

#### B. 与我的方案冲突的点，及取舍理由（5 条）

| # | 参考材料的观点 | 我的方案 | 取舍理由 |
|---|---|---|---|
| B1 | 硬件选 **Orange Pi Zero 2W**（¥130，30×65mm） | **BBB** | 硬门槛冲突：Zero 2W 的 H618 板级不开源（只有原理图 PDF，无 Gerber/可编辑源，datasheet 需 NDA），不满足 L1。**这是用户已明确的硬约束，不是性能之争** |
| B2 | 核心用 **Go（BSD-3）+ gomobile 出 .aar** | **Rust（MIT）+ cdylib + 手写 JNI** | ① AAR 体积 10–20MB vs Rust ≈2–4MB；② gomobile 的 JNI 调用开销对逐帧音频不友好；③ Go GC 停顿会打断流式 TTS；④ Rust 能同一份代码编到 armv7（BBB），Go 交叉编译到 ARMv7 硬浮点需额外处理。**不是 Go 不好，是这个场景 Rust 更合适** |
| B3 | **Piper 列为「MIT，可商用」** | **Piper 全线禁用** | **这是参考材料的硬性事实错误**：`rhasspy/piper` 代码确实是 MIT（我 2026-11-06 抓取确认），但它依赖 `piper-phonemize` → 链接 `espeak-ng` → **GPL-3.0**（已抓取 `COPYING` 确认）。代码 MIT 不等于产物 MIT。且 piper 已迁到 `OHF-Voice/piper1-gpl`，仓库名直接写了 GPL |
| B4 | 用 **configfs HID gadget** 让设备模拟鼠标 | **内嵌成品 USB 鼠标模块** | 语义错误：HID gadget 是让 AD 变成「另一台电脑的鼠标」，而 AD 本身是要有光标的**主机**。方向反了。D3 用成品模块正好绕开 |
| B5 | 保留 **锂电池 + TP4056** 充电 | **已取消电池，DC 5V 直供** | 用户在 v2 阶段已明确取消电池（运输合规 + 安全 + 成本），参考材料未跟上 |

| # | 参考材料的说法 | 问题 | 我的修正 |
