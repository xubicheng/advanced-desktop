## 第三轮（v3）：决策闭环

**用户拍板**
- D1 = β BeagleBone Black（L1，720p，单核 1GHz，¥550 级）；
- D2 = 坚持真鼠标形态，不做掌托式；
- D3 = 直接内嵌成品 USB 鼠标模块，不做 PMW3389 自研（光学腔问题消失）；
- D4 = 先 Android，再 Linux 硬件端，但目标平台要覆盖 Windows 10+ 与 Linux；
- D5 = 严格宽松许可（只允许 Apache/MIT/BSD），**不把 GPL 库链接进核心，允许 GPL 工具以独立进程 / CLI 调用**。

**其他要求**
- 逐条算清 β 的六项工程连带代价（外壳尺寸、USB Hub、720p、单核性能、micro-HDMI 与供电、断供降级链），不许回避。
- 采购淘宝优先；线下只买通用件；给总预算。
- 建 public 仓库，三许可分层，先加 `.gitignore` 再首次提交，纪要脱敏。
- 里程碑汇报：Android 最小链路成型先报一次；仓库推送成功立刻报。
- 诚实优先，不得编造型号/价格/供货/性能/许可证。

**产出**：v3 方案 + Android 先行周计划 + 许可清单 + 采购清单 + DECISIONS + CHANGELOG。

**关键结论（都是硬事实）**
- 外壳下限 **132×76×40mm**，重 **250–300g**（常规重鼠的 2 倍）；
- 单核 1GHz 上 whisper tiny 慢 5–10 倍 → **本地 STT/TTS 判死**，只留预录提示音；
- 供电必须 **DC 5V/4A**，峰值 2.76A，入口 ≥4.90V；
- BBB 断供的 L1 降级链：BBB → BBB Wireless → BeagleBone Green → BeaglePlay（破形态）→ 暂停，**不退回专有板**。

## 第四轮（v4）：概念模型修正

**用户澄清**（推翻 v3 的理解）
- 不是「AD 要做 Android 版 + Windows 桌面版 + Linux 桌面版」三套软件；
- 而是：**AD 本体的画面要能投到 Windows 10/11 与 Linux 桌面的显示器上**；
- AD 是那台无屏计算机，**显示器是别人的**；手机是 AD 的一种载体，屏幕可以息屏。

**用户给出的三条投屏路线**（要我给取舍而非罗列）
1. 自渲染 + 自有 Receiver（MJPEG over TCP）——倾向做 MVP；
2. scrcpy 路线（Apache-2.0）——做兜底；
3. WebRTC / 硬件 H.264——功能强但有许可与体积问题。

**我的取舍**
- **首选方案 1**：只有它能做到「AD 自己的画面」而不是「镜像整块手机」；只有它在息屏时天然成立；许可全宽松；体积最小；且 AD 的 UI 是状态驱动、帧率需求低，MJPEG 的带宽劣势几乎不存在。
- **方案 2 做兜底**，触发条件写死（需要 >20fps 或要看手机原生界面）。
- **方案 3 留架构位**（三个 trait：FrameSource / FrameEncoder / FrameTransport），给出 4 个升级切换点。

**技术纠偏**
- 用户建议「Android 自带 YuvImage/JPEG 编码」——方向对、API 错：`YuvImage` 吃 NV21，是给相机用的；我们自渲染的产物在 `Bitmap` 里，应该用 `Bitmap.compress(JPEG, q, out)`。

**反向输入**
- USB 鼠标模块（OTG）→ 读 HID 端点 → `PointerEvent` → TCP 上行 → Windows `SendInput` / Linux `/dev/uinput`。
- 与 BBB 端**共用同一份事件结构体**，只是注入后端不同。
- 「AD 当别人的鼠标」这条链路天然成立。

**如实说明的边界**
- Windows 的 UAC 提权窗口、锁屏、安全桌面**收不到 SendInput**——这是系统安全边界，不是 bug；
- Linux 的 `/dev/uinput` 需要 `input` 组或 udev 规则，**不是开箱即用**；
- Android 的 USB 设备授权每次插拔可能弹框；
- 息屏后厂商 ROM 可能限流，帧率会掉，需实测。

**产出**：v4 方案（概念模型、投屏三方案取舍、Mermaid 数据流图、反向输入、息屏实测计划 T1–T6、兼容基线、能力差异表、新增风险 7 条）+ CHANGELOG v4.0。
